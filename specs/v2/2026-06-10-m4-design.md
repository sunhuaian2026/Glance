## 1. M4 一句话定位

> Glance 的核心命脉 —— 把后台已经算好的「完全相同重复」结果搬到台前：侧边栏 一个「重复清理」入口，主区一张总览，量化「你有 X 组重复 · 可省 Y GB」，勾选整组即可一键移废纸篓省硬盘空间。看图是辅助，清理才是初心。

---

## 2. M4 范围

### 2.1 第一刀范围（M4 deliverables）

1. **全库重复组聚合查询** — 新增 SQL，把 `content_sha256` 相同且 `COUNT(*) > 1` 的图聚成「重复组」，每组算出可省空间。
2. **重复清理总览视图** — 侧边栏 一等入口 + 主区独立总览 view（重复组列表 + 每组缩略图 + 总可省空间数字 + 透明标注每组保留哪张）。
3. **整组勾选 + 一键移废纸篓** — 勾选要清理的组 → 一键把组内 `dedup_canonical=0` 的副本移入系统废纸篓。
4. **可撤销 banner** — 移完 ContentView 级 banner「已移 N 张到废纸篓 [撤销] [×]」（D33，跨视图持久），撤销 = 走显式回补 contract 走 FileManager 从废纸篓复原 + 重建 DB row（D34）。
5. **删后 DB 一致 + 总览刷新** — 真实移废纸篓成功 → 删对应 DB row → 受影响组 `reEvaluateGroup` 重决议 → 总览刷新。

### 2.2 不做什么（M4 scope freeze）

- **视觉相似去重**（Vision feature print 那套）—— 完全相同（SHA256 字节级）是第一刀，相似图清理放后续任务。理由：字节级完全相同 = 删哪张画质都一样，是最安全的第一刀。
- **逐张改保留**（不给「这组我要保留另一张」的能力）—— 完全相同像素无差别，保留哪张都一样，自动 canonical 即可（D28）。
- **跨格式 / 转码识别**（同一图存成 jpg + png 不算重复）—— candidate group 先撞 `(file_size, format)` 再 SHA256，跨格式天然不进同组，符合「第一刀最安全」。
- **「重新扫描」按钮** —— 信任后台索引自动维护（D31）。
- **批量删整库 / 永久删除**（只走废纸篓，永久删除由用户在 Finder 清空废纸篓决定）。
- **Schema 变更** —— M4 不加列，复用 v2 schema 已有 `content_sha256` / `dedup_canonical`。

## 3. M4 plan-time 决策（D28-D35，编入 `specs/Roadmap.md` V2 决策段）

> 接 M2/M3 已有 D11-D27 往后排（grep 确认现有最大 D 编号 = D27；D-OW 系列是 OpenWith 独立命名空间，不冲突）。

| **D33** | **撤销 UI 从 toast 升级为 ContentView 级 banner overlay**（codex review 第一轮 P1 撤销绑视图地雷 + codex review 第二轮 P1 QV 独立窗口现实 + P2 措辞精化）。撤销不再依附 DuplicateOverviewView 生命周期：移废纸篓后 banner 挂在 ContentView 全局层，**用户切走主区到 V1 folder / 智能文件夹 / 搜索 / 重复清理总览时 banner 持久可见可点**。**快速看图器在场期间 banner 不可见但状态保留**（快速看图器走独立 NSWindow `MainQuickViewerWindowController`，commit `ebd88bf` 后从 ContentView ZStack 迁出，物理上 ContentView overlay 看不到，ContentView.swift:124-125/231 确认）；快速看图器关闭后 banner 回归可见，仍可点撤销；**快速看图器在场期间 banner 不自动消失计时**（避免用户在 QV 里看图，自动 dismiss 时长跑完导致回到主区 banner 已没）。banner 默认不自动消失（需手动 × 关 或 「撤销」），消失计时改用相对长时长（30s）或显式 dismiss，**作废原 toast 1.5s 时长方案**。Banner 内含「已移 N 张到废纸篓 [撤销] [×]」结构。 | 原 D30 toast 方案绑 DuplicateOverviewView 生命周期 → 切走视图 → toast 卸载 → 文件已进废纸篓但 UI 不再给撤销机会 = 安全闭环被打穿。banner overlay 跨视图持久解决主区切换场景；快速看图器是独立 NSWindow architectural 现实在此明示，避免把"跨视图持久"叙事误读为"快速看图器期间也可见"。顺带吸收 spike finding（撤销路径无需 bookmark 持久化，in-memory 配对即足，see 风险段原 6 已合并到本 D33 注释）。**未动 D30 决策本身**（仍是无确认框 + 可撤销路径），只升级 UI 形态。 |
| **D34** | **撤销回补 DB 走显式 contract，禁止依赖 FSEvents 时机**（codex review 第一/二/三轮 P1 联合收）。restore 成功（FileManager.moveItem 把废纸篓内 URL 移回原 fullPath 成功）→ TrashService 立即返回成功 member 列表 + 删前预 fetch 的完整 `IndexedImageSnapshot`（字段见 4.5.1，对齐 images 表全部非 PK 列，含 dedup_canonical / feature_print 系列 / exif_capture_date 三族 IndexedImage struct 不含的列）→ DuplicateOverviewModel 同步走显式回补路径：**首选** `IndexStore.restoreImageFromSnapshot(_:)` 新 API（4.5.2 签名 spec，task 2 必装；同步返回 row id，写入失败抛错，调用方拿 id 立即 reEvaluateGroup + load() 无 race）→ 立即 `DedupPass.reEvaluateGroup(store:fileSize:format:)` 重决议 → 总览刷新；**降级** 若 snapshot 信息不全 / restoreImageFromSnapshot 抛 UNIQUE 冲突 / 业务认为该走 FolderScanner 兜底 → 显式触发 `FolderStoreIndexBridge.requestRescan(folderId:relativePath:) async throws -> Int64` 新 API（4.5.3 签名 spec，task 2 必装；async 返回时 row 已恢复或明确失败，codex review 第三轮 P2 禁 fire-and-forget；退化代价 = dedup_canonical / feature_print / exif 列由后台异步补齐，撤销立即"图回来"但 V2 找相似图 / 搜索可能需后台跑完几秒到几分钟）。**禁止**：`load()` 等 FSEvents 自动到达。**snapshot 保真完整性**（codex review 第三轮 P1 收）：原 design 假设"IndexedImage struct = 完整 snapshot" 实际不成立 —— IndexedImage struct (IndexedImage.swift:5-22) 缺 dedup_canonical / feature_print 系列 / exif_capture_date 三族列；若直接用 IndexedImage 当 snapshot 撤销会静默丢失 M2 找相似图 + M3 搜索元数据 → V2 能力退化。4.5.1 新建 IndexedImageSnapshot 值类型对齐 schema 所有列保真，TrashService 走新 query `fetchSnapshotForRestore` SELECT 全列。 | 原 5.2 撤销路径写"靠 FSEvents/下次 scan 重新 index"是 known-unknown，"撤销成功后分组没回来"的体感失败。contract 写死 → 撤销闭环可观测可保证；spike finding 已证 restore 不需要额外授权；snapshot schema 全列保真避免 V2 能力静默退化。restoreImageFromSnapshot + requestRescan + fetchSnapshotForRestore 三个 API 都是 task 2 解锁前置，task 1 不涉。|
| **D35** | **总览不是快照，订阅 `FolderStoreIndexBridge` 多播 observer fan-out 跟后台索引活动**（codex review 第一轮 P1 快照 vs 活视图 + 第二轮 P1 hook 现实纠正 + 第三轮 P1 ownership 拍板）。**bridge 一次性架构升级**（task 1 必做前置，影响 ContentView 既有 callee）：把 `var onIndexChanged: (() -> Void)?` 单播变量升级为多播 observer 容器 API —— `func addIndexChangedObserver(_ closure: @escaping () -> Void) -> UUID` / `func removeIndexChangedObserver(_ id: UUID)`，内部 `[UUID: () -> Void]` 字典；所有 fire 点（:87/:192/:202/:245）改成遍历 dict 调用每个 observer。**已有调用方** `ContentView.swift:584` 的 `bridge.onIndexChanged = { Task { await storeRef.refreshSelected() } }` 同步迁移成 `let token = bridge.addIndexChangedObserver { ... }`，token 持到 ContentView wireIfReady 域（@StateObject 持有 model 时存活）。DuplicateOverviewModel `init` 时 `bridge.addIndexChangedObserver { [weak self] in self?.scheduleReload() }` 拿 token，**deinit 时 removeObserver** (model 因 @StateObject 寿命与 ContentView 重建绑定，可在 ContentView 不再需要时显式调 removeObserver；不依赖 deinit 自动释放，避免 ContentView 长寿场景下 observer 永久挂着)。**`IndexStoreHolder.$progress` 不作为重复组刷新触发源**，只用于进度 chip 显示（mirror IndexingProgressView）。「直读现成」改为「直读现成 + 后台索引推动刷新」；D31 措辞同步从「直读 DB 现成 dedup 结果秒开」精化为「打开总览 → 立即直读现成秒开 + 多播 observer 推动自动刷新」。Combine 实现：bridge fire 点是非异步 closure，model 内 `scheduleReload()` 用 `DispatchWorkItem` 或 `Task` + 状态 flag 自维护 debounce 500ms 后 `load()`，不引入 PassthroughSubject。 | 第三轮 codex 抓出 ownership 问题：bridge.onIndexChanged 是单播变量，ContentView 已绑给 smartFolderStore.refreshSelected (:584 现网真实流量)；DuplicateOverviewModel 直接覆盖会断 smartFolder 流量（V2 主线 grid 刷新坏）。capture-old-callback 链式调用在 @StateObject 模型下不成立（model 长寿不 deinit → 永久覆盖）。一次性架构升级 bridge → 多播容器是正解：所有现有/未来观察者 fan-out 干净，无竞争。该升级属 task 1 必做前置（V1 ContentView.swift:584 必须同步迁），不阻塞 M4 主线（迁徙规模小：1 个写入点 + 4 个 fire 点 + N 个 caller，N=2，task 1 = smartFolder + dup overview）。|

### 4.4 新增聚合查询（真实列名核对）

核对 `IndexStoreSchema.swift:54-78` images 表真实列名：`id` / `content_sha256 TEXT`（NULLable）/ `dedup_canonical INTEGER`（NULLable）/ `file_size INTEGER NOT NULL` / `folder_id INTEGER NOT NULL` / `relative_path TEXT NOT NULL` / `url_bookmark BLOB NOT NULL`。folders 表有 `root_path TEXT`（root 行非 NULL）。

**dedup_canonical 口径**（DedupPass.swift:46-83 + IndexedImage.swift `promoteOrphanDuplicates` 重新核对，P2-3 修正）：
- `dedup_canonical = 1` → 保留张（canonical）。`reEvaluateGroup` 对**单 SHA256 / file_size+format 唯一组**也写 `=1`（DedupPass.swift:83），所以"唯一 SHA"在实际 DB 里是 `=1` 而非 NULL。
- `dedup_canonical = 0` → 待清理副本（duplicate）。
- `NULL` → 主要表示**未进入 candidate group / 尚未计算 SHA256 / 计算失败**（如 IO 错 / scope fail）；不是"单一图永久态"。M4 总览聚合查询 `WHERE content_sha256 IS NOT NULL` 已自动排除 NULL 行不进总览，无需特殊处理。

聚合查询设计（待 writing-plans 精化绑定，禁 string 拼用户输入；本查询无用户输入，全静态 SQL）：

```sql
-- 总览主查询：列出所有「真有重复副本」的组
SELECT content_sha256,
       COUNT(*) AS member_count,
       SUM(CASE WHEN dedup_canonical = 0 THEN file_size ELSE 0 END) AS reclaimable_bytes
FROM images
WHERE content_sha256 IS NOT NULL
GROUP BY content_sha256
HAVING SUM(CASE WHEN dedup_canonical = 0 THEN 1 ELSE 0 END) > 0
ORDER BY reclaimable_bytes DESC;
```

> `HAVING SUM(dedup_canonical=0) > 0` 而非 `COUNT(*) > 1`：只列**真有待清理副本**的组。DedupPass 已保证每组恰好一张 `=1`、其余 `=0`；NULL/单张组不进总览。

每组成员明细（点开组 / 删除时用），按 sha256 拉成员 + JOIN folders 拿 fullPath + 标注谁是 canonical：

```sql
SELECT i.id, i.dedup_canonical, i.file_size, i.folder_id, i.relative_path,
       i.url_bookmark, f.root_path || '/' || i.relative_path AS full_path
FROM images i
JOIN folders f ON i.folder_id = f.id
WHERE i.content_sha256 = ?
ORDER BY i.dedup_canonical DESC, i.birth_time ASC;
```

> `dedup_canonical DESC` 把保留张（=1）排第一，UI 透明显示「保留这张」（D28 约束）。`url_bookmark`（root bookmark）+ `folder_id` + `relative_path` 一起取，给 TrashService 复刻 DedupPass.computeSha 的 scope+拼接模式，**和** `deleteImage(folderId:relativePath:)` 删 DB row 用。

> 缩略图：总览每组显示 1-2 张缩略图即可（保留张 + 第一张副本），复用 `ThumbnailCell`（已被 EphemeralResultView / SmartFolderGridView 复用）。URL = resolve root bookmark + appendingPathComponent(relativePath)，同 `computeV2Urls`（ContentView.swift:499）pattern。

#### 4.5.2 `IndexStore.restoreImageFromSnapshot(_:)` 新 API

extension IndexStore {

#### 4.5.3 `FolderStoreIndexBridge.requestRescan(folderId:relativePath:) async throws` 新 API

extension FolderStoreIndexBridge {

## 6. 错误处理边界

| 场景 | 处理 |
|---|---|
| **security scope 失效**（盘没挂载 / bookmark stale）| `URL(resolvingBookmarkData:)` 抛错或 `startAccessingSecurityScopedResource` 返 false → 该 member 标记失败，不删其 DB row，banner 汇总「N 张成功，M 张失败（盘未连接？）」。stale bookmark 不在 M4 修复范围（属索引层），只如实报失败。 |
| **文件已被外部删除**（DB 有 row 但磁盘没文件）| `FileManager.trashItem` 抛 `NSFileNoSuchFileError` → 视作「已经不占空间了」，**仍删 DB row**（清理 stale 索引），计入「已清理」但不计废纸篓张数。 |
| **移废纸篓失败**（权限 / IO）| 该 member 失败，保留 DB row，banner 汇总失败数。不中断其余 member（逐个 try，失败累积不抛）。 |
| **撤销失败**（废纸篓里文件被用户手动清空 / 移走）| restore 抛错 → banner「部分文件无法复原（可能已清空废纸篓）」，已复原的正常。撤销是 best-effort。 |
| **撤销时原 fullPath 已被新文件占用**（P2-1，codex review 第一轮）| `FileManager.moveItem(at: trashURL, to: originalFullPath)` 在 target 存在时直接抛 `NSFileWriteFileExistsError`。policy：**失败累积报告 + banner 提示「M 张无法复原（路径已被占用），建议去 Finder 处理」**。**不擅自改名**（避免污染用户文件名空间）、**不擅自覆盖**（避免破坏用户新文件）。已复原的正常。 |
| **删除中 DB 被后台索引并发改**（FSEvents 同时增量）| IndexStore mutations 走自己 serial queue（DedupPass.swift 注释确认），删 row + reEvaluateGroup 与后台 dedup 串行不打架；load() 拿最新快照。FSEvents 在 trash 中触发的 Created/Removed 事件（trashItem 会触发原路径 Removed）由 FolderStoreIndexBridge 现有 handle 路径吸收，与 M4 显式删除幂等（同一 row 不会重复删）。 |
| **撤销机制时效** | banner 存活期 `DS.Dedup.bannerAutoDismissSeconds`（30s，或纯手动 dismiss，writing-plans 定）；过期后文件仍在废纸篓，用户可去 Finder 手动复原（系统能力，非 Glance 范围）。**与原 toast 1.5s 时效问题彻底解决**（D33）。 |
| **删除中用户切走主区或 app quit**（codex review 第一轮 P1 衍生 + 第二轮 P2 quit 机制）| `DuplicateOverviewModel.isTrashing=true` 期间用户切 V1 folder / 智能文件夹 / 搜索 / 重复清理总览：删除任务**继续在后台跑**（@MainActor model 持有 state），删完 banner 自动出现在新主区上方（D33 全局 overlay）；切到快速看图器：删除仍跑，banner 不可见但状态保留，QV 关闭后 banner 回归（D33 QV architectural 现实）。**app quit / ⌘Q**：接受 quit = 取消 policy（codex review 第二轮 P2）—— CancellationToken cascade cancel TrashService 剩余 trash 任务，已 trashed member 文件保留在系统废纸篓，banner state in-memory 丢失下次启动不出现 banner，**用户仍可 Finder 手动复原**（系统能力）。**不引入 quit interception**（不动 SwiftUI quit 流程，避免 task 2 实施期间引入新风险）。 |
| **大批量删除**（P2-2，1000+ 张量级，codex review 第一轮）| 进度回调（每 50 张 publish）+ banner 显示进度文案 + 取消按钮（cancellation token 中断剩余 member trash）。已完成的 member 正常进 successes；剩余的不动；banner 汇总「已移 X 张，已取消 Y 张」。**单组内 member 不拆原子**（一组要么全 trash 要么全不动，避免 reEvaluateGroup 半截组态紊乱）。 |
| **卷类型差异**（P2-4，codex review 第一轮）| **只读卷**（CD-ROM / dmg mount / 加密只读盘）：`trashItem` 抛 `NSFileWriteVolumeReadOnlyError` → member 失败累积。**卷被弹出**（移动盘睡眠 / 用户手动 unmount）：`startAccessingSecurityScopedResource` 返 false 或 `trashItem` 抛 `NSFileReadNoSuchFileError` / IOError → member 失败。**iCloud Drive**（数据未本地化）：`trashItem` 可能成功也可能抛错（系统隐式下载或拒绝），按 trashItem 结果如实报；**网络盘 / NFS / SMB**：无系统级 Trash 概念，`trashItem` 行为依赖卷支持，常报错 → 失败累积；**磁盘满**：`NSFileWriteOutOfSpaceError` → 失败累积 + banner 单独提示「磁盘已满」。**所有卷类型差异统一在 member 级 best-effort + 失败累积 + banner 汇总**，不在 task 2 实施初期为单卷类型加特殊路径（writing-plans 阶段定真机验矩阵）。 |

## 9. 待军哥确认的风险（Read 代码后发现，未擅自改决策）

1. ~~**toast 撤销时长 1.5s 太短**~~ **(✅ RESOLVED by D33, 2026-06-16 codex review 第一轮)**。原议：用独立常量 `DS.Dedup.undoToastDurationSeconds`（6-8s）或改 banner。codex review 第一轮 P1-1 抓出 D29 ephemeral 挂载模式有更深问题（撤销绑视图生命周期），引入 D33 一次性彻底解决（toast → ContentView 级 banner overlay，30s 或纯手动 dismiss）。本风险条目作废，留作 changelog 历史。

2. **`FileManager.trashItem` 跨 root 的 security scope** — **spike 部分验通（2026-06-16）**。
   - **容器内场景 ✅ 已通**：sandbox app 对自己 `Application Support` 容器内造的测试文件 `trashItem` + `restoreItem` 全 OK；`resultingItemURL` 正常返回，是 sandbox app 立即可访问的 `~/.Trash/...` 句柄，restore 不需要额外授权（spike `Glance/_SpikeSandboxTrash.swift` 已 `git checkout` 弃）。

3. ~~**撤销后文件重新进 DB 的时机**~~ **(✅ RESOLVED by D34, 2026-06-16 codex review 第一轮 + 第二轮 API reality 纠正)**。第一轮 codex 升级到 contract 级别——禁止依赖 FSEvents 时机，restore 成功后立即走显式回补路径（首选 `restoreImageFromSnapshot` 重建 row + 降级 `requestRescan` 单文件 rescan，两个 API task 2 实施前置新建）。本风险条目作废，contract 见 D34 + 5.2 数据流。

6. ~~**撤销路径可能简化（spike 副产 finding）**~~ **(✅ RESOLVED, 折入 D33/D34，2026-06-16 codex review 第一轮)**。原 finding 已分别合并到 D33（in-memory 配对 banner / 不持久化）+ D34（restore 后显式回补 DB row 不需要 bookmark 跨 session）。本风险条目作废。跨 root 边界仍归风险 2 PENDING 部分。

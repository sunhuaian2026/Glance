## 1. M4 一句话定位

> Glance 的核心命脉 —— 把后台已经算好的「完全相同重复」结果搬到台前：侧边栏 一个「重复清理」入口，主区一张总览，量化「你有 X 组重复 · 可省 Y GB」，勾选整组即可一键移废纸篓省硬盘空间。看图是辅助，清理才是初心。

## 2. M4 范围

### 2.1 第一刀范围（M4 deliverables）

1. **全库重复组聚合查询** — 新增 SQL，把 `content_sha256` 相同且 `COUNT(*) > 1` 的图聚成「重复组」，每组算出可省空间。
2. **重复清理总览视图** — 侧边栏 一等入口 + 主区独立总览 view（重复组列表 + 每组缩略图 + 总可省空间数字 + 透明标注每组保留哪张）。
3. **整组勾选 + 一键移废纸篓** — 勾选要清理的组 → 一键把组内 `dedup_canonical=0` 的副本移入系统废纸篓。
4. **可撤销 toast** — 移完顶部 toast「已移 N 张到废纸篓 [撤销]」，撤销 = 从废纸篓复原。
5. **删后 DB 一致 + 总览刷新** — 真实移废纸篓成功 → 删对应 DB row → 受影响组 `reEvaluateGroup` 重决议 → 总览刷新。

### 2.2 不做什么（M4 scope freeze）

- **视觉相似去重**（Vision feature print 那套）—— 完全相同（SHA256 字节级）是第一刀，相似图清理放后续任务。理由：字节级完全相同 = 删哪张画质都一样，是最安全的第一刀。
- **逐张改保留**（不给「这组我要保留另一张」的能力）—— 完全相同像素无差别，保留哪张都一样，自动 canonical 即可（D28）。
- **跨格式 / 转码识别**（同一图存成 jpg + png 不算重复）—— candidate group 先撞 `(file_size, format)` 再 SHA256，跨格式天然不进同组，符合「第一刀最安全」。
- **「重新扫描」按钮** —— 信任后台索引自动维护（D31）。
- **批量删整库 / 永久删除**（只走废纸篓，永久删除由用户在 Finder 清空废纸篓决定）。
- **Schema 变更** —— M4 不加列，复用 v2 schema 已有 `content_sha256` / `dedup_canonical`。

### 4.4 新增聚合查询（真实列名核对）

核对 `IndexStoreSchema.swift:54-78` images 表真实列名：`id` / `content_sha256 TEXT`（NULLable）/ `dedup_canonical INTEGER`（NULLable）/ `file_size INTEGER NOT NULL` / `folder_id INTEGER NOT NULL` / `relative_path TEXT NOT NULL` / `url_bookmark BLOB NOT NULL`。folders 表有 `root_path TEXT`（root 行非 NULL）。

**dedup_canonical 口径**（DedupPass.swift 注释 + IndexedImage.swift `promoteOrphanDuplicates` 确认）：
- `dedup_canonical = 1` → 保留张（canonical）。
- `dedup_canonical = 0` → 待清理副本（duplicate）。
- `NULL` → 不在任何 candidate group（file_size+format unique）或单 SHA256，**视作 canonical，永远不删**。

聚合查询设计（待 writing-plans 精化绑定，禁 string 拼用户输入；本查询无用户输入，全静态 SQL）：

```sql
-- 总览主查询：列出所有「真有重复副本」的组
SELECT content_sha256,
       COUNT(*) AS member_count,
       SUM(CASE WHEN dedup_canonical = 0 THEN file_size ELSE 0 END) AS reclaimable_bytes
FROM images
WHERE content_sha256 IS NOT NULL
GROUP BY content_sha256
HAVING SUM(CASE WHEN dedup_canonical = 0 THEN 1 ELSE 0 END) > 0
ORDER BY reclaimable_bytes DESC;
```

> `HAVING SUM(dedup_canonical=0) > 0` 而非 `COUNT(*) > 1`：只列**真有待清理副本**的组。DedupPass 已保证每组恰好一张 `=1`、其余 `=0`；NULL/单张组不进总览。

每组成员明细（点开组 / 删除时用），按 sha256 拉成员 + JOIN folders 拿 fullPath + 标注谁是 canonical：

```sql
SELECT i.id, i.dedup_canonical, i.file_size, i.folder_id, i.relative_path,
       i.url_bookmark, f.root_path || '/' || i.relative_path AS full_path
FROM images i
JOIN folders f ON i.folder_id = f.id
WHERE i.content_sha256 = ?
ORDER BY i.dedup_canonical DESC, i.birth_time ASC;
```

> `dedup_canonical DESC` 把保留张（=1）排第一，UI 透明显示「保留这张」（D28 约束）。`url_bookmark`（root bookmark）+ `folder_id` + `relative_path` 一起取，给 TrashService 复刻 DedupPass.computeSha 的 scope+拼接模式，**和** `deleteImage(folderId:relativePath:)` 删 DB row 用。

> 缩略图：总览每组显示 1-2 张缩略图即可（保留张 + 第一张副本），复用 `ThumbnailCell`（已被 EphemeralResultView / SmartFolderGridView 复用）。URL = resolve root bookmark + appendingPathComponent(relativePath)，同 `computeV2Urls`（ContentView.swift:499）pattern。

## 5. 数据流

### 5.1 总览加载（任务 1）

```
后台索引（已有，不动）
  FolderScanner 扫完 → triggerDedupFullPass → DedupPass.runFullPass
    → fetchCandidateGroups (file_size,format) → 各组 SHA256 → setDedupCanonical
  FSEvents 增量 → triggerDedupGroup → reEvaluateGroup
  ⇒ DB 里 dedup_canonical 始终是最新决议（D31 信任来源）
        │
        ▼
侧边栏 点「重复清理」(D29)
  → ContentView showDuplicateOverview = true（清其他三态）
  → DuplicateOverviewModel.load()
       → IndexStore.fetchDuplicateGroups()（4.4 聚合查询，秒开）
       → 组装 [DuplicateGroup]（canonical 标注 + reclaimableBytes）
       → @Published groups 更新
        │
        ▼
DuplicateOverviewView 渲染
  顶部统计条：「X 组重复 · 可省 Y」(ByteCountFormatter)
  每组：保留张缩略图(标「保留」badge) + 副本缩略图 + 组可省空间 + 整组 checkbox
  后台仍在索引 → 顶部 IndexingProgressView chip（复用 indexStoreHolder.progress）
```

### 5.2 删除闭环（任务 2）

```
用户勾选 N 组 → 点「移入废纸篓」(D30，无确认框)
  → DuplicateOverviewModel.trashSelected()
       → 收集所选组的 duplicates（dedup_canonical=0 成员，保留张永不入列）
       → TrashService.trashItems(members)
            对每 member：resolve root bookmark + startAccessingSecurityScopedResource
                       + 拼 child URL + FileManager.trashItem(at:resultingItemURL:)
                       （复刻 DedupPass.computeSha scope 模式；记录废纸篓新位置 URL）
       → 对每个成功移走的 member（按 folder_id + relative_path）：
            deleteImage(folderId:relativePath:)  删 DB row（已有 :109）
       → 对每个受影响 sha256 的组：
            删前已经 fetchImageGroupKey 取到 (file_size, format)
            → DedupPass.reEvaluateGroup(store:fileSize:format:) 重决议剩余组（已有 :46）
            （若组内只剩保留张 → reEvaluateGroup 自动清回 canonical=true，组从总览消失）
       → promoteOrphanDuplicates() 兜底（已有 :391）
       → DuplicateOverviewModel.load() 重新聚合 → 总览刷新
       → toast「已移 N 张到废纸篓 [撤销]」(D30, DS.About.toastDuration)
        │
        ▼
点 [撤销]（toast 存活期内）
  → TrashService.restoreItems(已记录的废纸篓 URL → 原 fullPath)
  → 复原成功的文件 → 下一次 FSEvents/scan 会重新 index（或主动 re-load）
  → load() 刷新总览
```

> 删 DB row 与文件移废纸篓的顺序：**先移文件成功、再删 DB row**。移废纸篓失败的 member 不删其 DB row（保持 DB 与磁盘一致，下次仍显示在总览，用户可重试）。

## 6. 错误处理边界

| 场景 | 处理 |
|---|---|
| **security scope 失效**（盘没挂载 / bookmark stale）| `URL(resolvingBookmarkData:)` 抛错或 `startAccessingSecurityScopedResource` 返 false → 该 member 标记失败，不删其 DB row，toast 汇总「N 张成功，M 张失败（盘未连接？）」。stale bookmark 不在 M4 修复范围（属索引层），只如实报失败。 |
| **文件已被外部删除**（DB 有 row 但磁盘没文件）| `FileManager.trashItem` 抛 `NSFileNoSuchFileError` → 视作「已经不占空间了」，**仍删 DB row**（清理 stale 索引），计入「已清理」但不计废纸篓张数。 |
| **移废纸篓失败**（权限 / IO）| 该 member 失败，保留 DB row，toast 汇总失败数。不中断其余 member（逐个 try，失败累积不抛）。 |
| **撤销失败**（废纸篓里文件被用户手动清空 / 移走）| restore 抛错 → toast「部分文件无法复原（可能已清空废纸篓）」，已复原的正常。撤销是 best-effort。 |
| **删除中 DB 被后台索引并发改**（FSEvents 同时增量）| IndexStore mutations 走自己 serial queue（DedupPass.swift 注释确认），删 row + reEvaluateGroup 与后台 dedup 串行不打架；load() 拿最新快照。 |
| **撤销机制时效** | toast 存活期（`DS.About.toastDurationSeconds`，当前 1.5s 偏短 → 见第 9 节风险，可能需为 M4 调长或改成可手动 dismiss）；过期后文件仍在废纸篓，用户可去 Finder 手动复原（系统能力，非 Glance 范围）。 |

## 7. 「透明显示每组保留哪张」UI 要求（D28 硬约束）

- 每个重复组**必须**视觉标出哪张是保留张（`dedup_canonical=1`）：保留张缩略图加「保留」badge（DS.Dedup 配色，绿/accent 系，禁硬编码）+ 副本缩略图视觉弱化（无 badge 或灰化）。
- 保留张**不可勾选删除**（checkbox 只控整组的「清掉副本」，保留张永远留下）。
- 组内显示保留张的**来源路径**（root 名 + relative_path，mirror SmartFolderGridView cell tooltip 显完整路径的做法），让用户知道「保留的是哪个文件夹里那张」。
- 即便不让改保留，用户看得到 = 建立信任（DRAFT 决策 1 约束原文）。

## 8. 任务拆分（两片，风险前置）

### 8.1 任务 1 — 只读总览（可独立 ship）

**范围**：聚合查询 + 侧边栏 入口 + 主区总览 view（重复组 + 缩略图 + 保留标注 + 可省空间统计），**只读不删**。

**新增**：`fetchDuplicateGroups` 聚合查询 / `DuplicateGroup` record / `DuplicateOverviewModel`（仅 load）/ `DuplicateOverviewView`（含统计条、组列表、保留 badge、空态、索引 chip）/ `SmartFolderListView` 入口项 / ContentView 挂载 + 互斥。

**任务 三标准论证**：
- **端到端可跑**：侧边栏 点入口 → 主区出现真实重复组 + 真实可省空间数字（读真 DB）。
- **用户可感知**：第一次量化「我有 X 组重复 · 可省 Y GB」（初心 awareness 时刻）。
- **独立可 ship**：无删除能力也有完整价值 —— 军哥真机先验证 dedup 结果准不准（保留张选对没、组分对没），**建立信任后再放开删除**，风险前置。

**边界**：本片不碰任何真实文件（零删除代码），最安全。

### 8.2 任务 2 — 删除闭环

**范围**：整组勾选 + 一键移废纸篓 + 可撤销 toast + 删 DB row + reEvaluateGroup + 总览刷新。

**新增**：`TrashService`（trashItems / restoreItems，**全项目首个碰真实文件的代码**）/ `DuplicateOverviewModel` 加勾选集合 + trashSelected + undo + 删后刷新 / `DuplicateOverviewView` 加 checkbox + 「移入废纸篓」按钮 + toast。

**复用既有**：`deleteImage` / `deleteImages` / `fetchImageGroupKey` / `reEvaluateGroup` / `promoteOrphanDuplicates`（全部已存在，无需改）。

**任务 三标准论证**：
- **端到端可跑**：勾组 → 点移废纸篓 → 文件真进系统废纸篓 + DB 同步 + 总览少一组 + toast 可撤销。

## 9. 待军哥确认的风险（Read 代码后发现，未擅自改决策）

1. **toast 撤销时长 1.5s 太短**（`DS.About.toastDurationSeconds = 1.5`）。这是为「复制提示」设的瞬时 toast。删除撤销窗口 1.5s 内用户来不及反应。**建议**（待拍板）：M4 用独立常量 `DS.Dedup.undoToastDurationSeconds`（如 6-8s）或改成「需手动点 × 关闭、不自动消失」的可撤销 banner。不改 D30 决策本身（仍是 toast + 撤销），只调时长参数。

2. **`FileManager.trashItem` 跨 root 的 security scope** — **spike 部分验通（2026-06-16）**。
   - **容器内场景 ✅ 已通**：sandbox app 对自己 `Application Support` 容器内造的测试文件 `trashItem` + `restoreItem` 全 OK；`resultingItemURL` 正常返回，是 sandbox app 立即可访问的 `~/.Trash/...` 句柄，restore 不需要额外授权（spike `Glance/_SpikeSandboxTrash.swift` 已 `git checkout` 弃）。
   - **跨 root 家目录场景 ❌ 仍 PENDING**：BookmarkManager 持的真实用户文件夹（如 `~/Documents/Photos`、外置盘）下的图片做 trash，sandbox 是否在同 root scope 下放行写操作 + 跨 root 多目录连环 trash 的 scope 边界，**spike 未覆盖**。本风险**主要部分仍开放**，留 PENDING-USER-ACTIONS 真机验 / 或本 session 用 macOS native 远程 CC 自闭环路径（全局 CLAUDE.md (c) 段补丁 5）跑跨 root spike 补验。若 sandbox 不放行跨 root 写，可能需要每个被删文件的细粒度授权 —— 会动 D30 的「一键」体验，**风险前置在 任务 2 真机验时暴露**。

3. **撤销后文件重新进 DB 的时机**。restore 把文件 move 回原 fullPath 后，要靠 FSEvents/下次 scan 重新 index 才回到 DB + 重算 dedup。撤销那一刻总览可能短暂不显示该组（直到重新 index）。**建议**：撤销成功后主动触发一次该 root 的 group 重评 / re-index，而非干等 FSEvents。待 writing-plans 阶段定具体钩子。

4. **`url_bookmark` 是 root bookmark 不是文件 bookmark**（IndexedImage.swift:7-9 明确）— **spike 强证模式可行（2026-06-16）**。TrashService 必须走「resolve root + 拼 relative_path」而非直接 resolve 文件 bookmark，否则拿不到文件 URL。容器内 spike 复刻 DedupPass.computeSha 的 `resolveBookmark → startAccessingSecurityScopedResource → URL(fileURLWithPath: rootURL.path + relativePath)` 模式真跑通了 trash + restore；剩跨 root 边界由风险 2 PENDING 部分覆盖。已在设计中按此处理，本注主要确认 review 重点。

5. **DedupPass 用 `(file_size, format)` 当 candidate group key，但总览聚合用 `content_sha256`**。删除后 `fetchImageGroupKey` 取的是 `(file_size, format)` 喂 `reEvaluateGroup`，与总览的 sha256 维度不同维。逻辑上自洽（同 sha256 必然同 file_size+format），但 writing-plans 阶段要确保「删某 sha256 组的副本 → reEvaluate 对应 (file_size,format) group」映射正确，避免漏重评。已在数据流 5.2 标注，列此供 review 重点核对。

6. **撤销路径可能简化（spike 副产 finding, 2026-06-16）**。原 D30 撤销机制设计假设需要在 toast 存活期内记住「废纸篓内每个 member 的新 URL」（`resultingItemURL` 数组），撤销时 `FileManager.moveItem(at: trashURL, to: originalFullPath)` 复原。spike 实证 `resultingItemURL` 是 sandbox app 立即可访问的句柄、restore 写回原 fullPath 不需要额外授权（容器内场景）。**暗示**：撤销路径无需引入额外 bookmark 持久化 / 跨 session 撤销机制 — 只在 in-memory `TrashOutcome` 数组保留 `[(originalFullPath, trashURL)]` 配对，toast dismiss 时丢弃 / 撤销时遍历 moveItem 即可。**未变 D30**（仍是 toast + 撤销路径），但实施复杂度降一档。跨 root 边界仍待 PENDING 验。writing-plans 阶段按此简化版拆 task。
